## 2. Technical Inconsistencies & Detailed Root-Cause Analysis

While the algorithmic implementation and reproduced numerical metrics match the project documentation with extraordinary fidelity, the technical audit identified **six nuanced implementation behaviors and discrepancies** that should be documented in your research report:

### Discrepancy 1: Integer Timestamps Parsed as Nanoseconds by `pd.to_datetime`
- **Report Claim / Expectation:** Timestamps in the synthetic datasets are simple integer seconds ($0, 1, 2, \dots, 119$).
- **Actual Code Behavior:** In `backend/data_processor.py:L57`, the code executes `pd.to_datetime(df["timestamp"], errors="coerce")`. When integers are passed to `pd.to_datetime`, pandas interprets integer values as nanoseconds since the Unix epoch (1970-01-01 00:00:00.000000000). The subsequent elapsed seconds formula:
  $$\Delta t = (t - t_0).\text{dt.total\_seconds}()$$
  converts nanoseconds to seconds by dividing by $10^9$. As a result, timestamp $35$ becomes $3.5 \times 10^{-8}$ seconds ($0.000000035$ s).
- **Secondary Impact on Episode Duration:** In `_build_episode()` (`ml_engine.py:L513`), episode duration is calculated as `duration = round(abs(end_ts - start_ts), 2)`. Because the difference between $3.8 \times 10^{-8}$ and $3.5 \times 10^{-8}$ is $0.000000003$, rounding to 2 decimal places yields `0.00`. This triggers the fallback code:
  ```python
  if duration == 0:
      duration = round(len(ep_records) * 0.3, 2)
  ```
  Consequently, synthetic episode durations become $0.9$ s (3 records), $0.6$ s (2 records), and $0.3$ s (1 record), which is based on the playback timer ($300$ ms per frame) rather than the physical driving time.
- **Recommendation for Report:** Document this as an implementation observation in Chapter 4 (Table 4.12). Note that in real-world telematics logs with ISO-8601 string timestamps (such as `Telematicsdata.csv`), `pd.to_datetime` parses accurately and computes real elapsed seconds (e.g., Episode EP-001 duration: $1,747.0$ s).

### Discrepancy 2: Ambiguous Sensor Mapping in Long-Format Telematics
- **Observed Behavior:** In `Telematicsdata.csv`, the dataset contains both `ENGINE COOLANT TEMPERATURE` and `AIR INTAKE TEMPERATURE`.
- **Mapping Result:** `AIR INTAKE TEMPERATURE` was mapped to the canonical `coolant_temp` feature, while `ENGINE COOLANT TEMPERATURE` was retained under its original name.
- **Root Cause:** In `data_processor.py:L13`, the alias list for `coolant_temp` includes `"ambient air temperature"` and `"temperature"`. During column iteration, `AIR INTAKE TEMPERATURE` achieved a token sort ratio $> 75$ against the aliases. Because `processed_cols.add(std_name)` prevents re-mapping to the same canonical feature, the subsequent column `ENGINE COOLANT TEMPERATURE` was kept under its unmapped name.
- **Recommendation for Report:** Document this in Chapter 4 (Table 4.12) as a limitation of greedy first-match fuzzy mapping. Propose prioritizing exact string matches or using a hierarchical mapping rule (e.g., map `engine coolant temperature` first, then map air temperature to an intake temperature feature).

### Discrepancy 3: Ground Truth Pulse Inversion & Recovery Framing
- **Injected Ground Truth:** In `create_samples.py`, the RPM spike is injected from points 35 to 37:
  ```python
  rpm[35:38] += 2500
  ```
- **Observed Detection:**
  - Record 35 is flagged as Consensus Anomaly ($v=2$) because $\text{rpm\_change} = \Delta \text{rpm} = +2241.0$ (Z-score 6.65).
  - Record 36 has steady elevated RPM ($4910 \rightarrow 4910$), meaning $\text{rpm\_change} \approx 0.0$. Neither IF nor LOF flagged record 36 because its static deviation fell slightly below the 5% contamination threshold. It was classified as Normal ($v=0$).
  - Record 37 is flagged as Weak Anomaly ($v=1$) by Isolation Forest.
  - Record 38 (when the RPM drops back to nominal $2410$) experienced $\text{rpm\_change} = -2589.0$ (Z-score 7.68). This was flagged by LOF and SVM ($v=2$, Consensus Anomaly).
- **Physical Interpretation:** Feature engineering with first-order differences ($\Delta x / \Delta t$) creates two distinct anomaly boundaries: the onset of the fault (positive derivative surge) and the recovery/collapse of the signal (negative derivative plunge). The Episode Grouping algorithm successfully bridges this gap because index 38 is within 2 frames of index 37, unifying both the fault onset and recovery into a single 3-record incident episode (EP-001).

### Discrepancy 4: Circular Health Score Client-Side Architecture
- **Report Expectation:** Health score is a system-wide analytical metric.
- **Code Reality:** In `Dashboard.tsx:L79-97`, the vehicle health score is managed as a React client-side state variable (`healthScore`). It dynamically decrements during SSE stream playback:
  $$\text{Penalty} = \text{votes} \times 6.0$$
  and recovers $+0.5$ per nominal frame. It is not calculated or persisted by `backend/ml_engine.py` or stored in `vehicleguard.db`.
- **Recommendation for Report:** Clearly describe the health score as a **real-time presentation-layer heuristic** that visualizes degradation during playback, whereas the **deterministic confidence score** and **consensus votes** are the authoritative machine learning outputs computed on the backend.

---

### Discrepancy 5: Subsampling Resolution Trade-off
- **Implementation:** In `data_processor.py:L64-67`, datasets with $> 1,000$ rows are subsampled using `step = ceil(N / 1000)`. For `Telematicsdata.csv` (173,853 pivoted rows), `step = 174`, reducing the analyzed data to exactly 974 records.
- **Trade-off Analysis:**
  - *Advantage:* Allows immediate, fluid browser rendering, responsive Recharts charts, and fast model retraining (< 220 ms) without requiring dedicated GPU clustering or distributed PySpark workers.
  - *Limitation:* Drops 173 of every 174 time-steps, meaning micro-second or transient electrical sensor glitches occurring between subsampled frames are omitted from analysis.
- **Recommendation for Report:** Highlight this as an intentional edge-computing architectural trade-off balancing real-time web responsiveness with historical data fidelity.

## 3. Reproducibility Statement

The VehicleGuard AI pipeline is **100% reproducible**:
